# Spark Caching and Distributed Execution

## 1. Question and motivation

This project asks when Spark caching improves an iterative application. The workload is PageRank over a deterministic directed graph. Each iteration reuses the same adjacency-list RDD, so the application exposes the tradeoff between the one-time cost of materializing cached partitions and the cost of recomputing the same lineage on every later iteration.

## 2. Architecture

The system uses one Spark driver and two local worker processes in `local-cluster[2,1,1024]`. The driver reads an edge list, groups outgoing neighbors into the shared `links` RDD, and executes repeated PageRank iterations. Each iteration joins `links` with the current ranks, emits contribution pairs, reduces by destination node, and materializes the new rank vector. The same partition count and resource limits apply to cached and uncached runs.

The cached configuration calls `links.persist(StorageLevel.MEMORY_ONLY)`. The uncached configuration uses the same RDD lineage without persistence. The application logs the Spark UI URL, partitions, storage level, initial materialization time, per-iteration time, and result checksum.

The editable architecture diagram is in `docs/architecture.md`; the presentation reproduces the same components and connections.

## 3. Implementation and correctness

The PageRank recurrence is:

`rank_new(v) = 0.15 / N + 0.85 * sum(rank(u) / out_degree(u))`.

The Spark implementation and the sequential reference use the same deterministic input, recurrence, number of iterations, and tolerance. The verifier compares every output node and reports the maximum absolute error. Cached and uncached runs must produce the same rank vector within the tolerance. The demo also records the checksum and the top five nodes so that the result remains easy to inspect.

The implementation uses the RDD design idea from Zaharia et al. (2012): an RDD can persist computed partitions for reuse, while lineage allows Spark to recompute lost partitions. The project simplifies the original cluster setting to two local workers and focuses on timing and observable stage behavior.

## 4. Experiment design

The required comparison uses three deterministic graph sizes, six PageRank iterations, four partitions, two worker processes, and two repetitions per cache configuration. The workload, partition count, JVM memory setting, and input seed remain fixed between cached and uncached runs. The first `count()` on `links` measures initial materialization separately. The remaining five timings measure reuse across subsequent iterations. Results are stored as raw JSON and CSV before analysis.

The analysis reports means and standard deviations. It produces a comparison of subsequent iteration time, a figure separating initial materialization from later reuse, and a partition-budget figure. A slowdown is a valid outcome: local startup overhead, small datasets, memory pressure, or the cost of materialization can dominate the benefit of avoiding recomputation.

## 5. Results and interpretation

The final measurements are generated by `scripts/run_experiments.ps1` and summarized in `results/summary.csv`. Each condition ran twice with six iterations and four partitions. Times below are seconds, reported as mean +/- standard deviation.

| Workload | Cache | Initial materialization | Later iterations | Total runtime |
| --- | --- | ---: | ---: | ---: |
| 2,000 edges | Off | 5.753 +/- 0.361 | 4.265 +/- 0.231 | 36.397 +/- 1.968 |
| 2,000 edges | On | 6.782 +/- 0.119 | 4.333 +/- 0.020 | 38.281 +/- 0.270 |
| 10,000 edges | Off | 5.932 +/- 0.074 | 4.450 +/- 0.046 | 38.044 +/- 0.201 |
| 10,000 edges | On | 6.772 +/- 0.059 | 4.427 +/- 0.089 | 38.559 +/- 0.448 |
| 30,000 edges | Off | 6.238 +/- 0.263 | 4.843 +/- 0.037 | 40.680 +/- 0.618 |
| 30,000 edges | On | 7.166 +/- 0.232 | 4.585 +/- 0.263 | 40.385 +/- 2.108 |

The measured subsequent-iteration speedup for caching was 0.984x on the small workload, 1.005x on the medium workload, and 1.056x on the large workload. This supports the expected mechanism but also shows its boundary: the first materialization cost makes caching slower on small inputs, while repeated reuse makes it useful on the largest input. The cached and uncached checksums were 1.0, and the sequential verifier passed with a maximum absolute error of approximately `5e-13` on the demo.

## 6. Limitations

All workers run on one laptop and share the same physical CPU, memory, and disk. The experiment therefore does not estimate the performance of a multi-machine Spark cluster. The graph is static, the workload uses RDDs rather than DataFrames, and the application does not claim fault tolerance beyond Spark's lineage-based recomputation model. The optional executor-failure and skew experiments are outside the core submission.
